LNMesh Build Report

Proof of concept · regtest · 3 × Raspberry Pi 5

LNMesh: Offline Lightning Channels over a Raspberry Pi Mesh

Two Lightning nodes with no internet connection open, use, and close payment channels through a gateway on a WiFi mesh. Every on-chain byte crosses the mesh; nothing else does.

Built and demonstrated 2026-09-03LND 0.19.2 · Bitcoin Core 29.1 · batman-adv 2025.4Debian 13 on Pi OS Lite

TL;DR

  • Prior work showed offline nodes can pay. This project shows they can also fund, open, and close channels, and punish a cheating counterparty, with no internet and no prior setup, because a gateway node on the mesh relays their transactions and their view of the chain.
  • All six demos pass on real hardware: offline funding, offline open, offline pay, cooperative and force close, paying with the gateway's Bitcoin node switched off, and a breach that gets punished one block later.
  • Nothing custom. Stock LND and Bitcoin Core, configured so the gateway serves compact block filters over the mesh and the offline nodes run as Neutrino light clients with the gateway as their only peer.
  • One finding changed the design: LND with a remote bitcoind backend cannot even start a payment while that backend is unreachable. Moving the offline nodes to Neutrino fixed it and also upgraded the trust model, from "the gateway is trusted" to "the gateway can censor but cannot lie".
  • Numbers: payments settle in about 260 ms over one mesh hop, an offline node's transaction reaches the gateway's mempool in about 1 s, the mesh carries 48 Mbit/s, and a breach was detected 4 s after the victim came back online.

What the contribution is

A Lightning payment needs only a connection to the channel peer. Opening a channel, closing one, or catching a cheat needs the blockchain: a UTXO to spend, a way to broadcast, and confirmations to watch. LNMesh (Kurt, Sahin, Harrilal-Parchment, Akkaya; WoWMoM 2023) demonstrated the first part over a mesh and assumed channels were opened while online.

This build removes that assumption. Nodes B and C have no cable and no internet. Node A has both and sits on the same mesh. A relays B's and C's transactions to the chain and serves them block headers and compact block filters, so B and C can do everything a Lightning node does while remaining physically offline. The point of the proof of concept is to show that end to end and to name the trust it requires.

Two findings that changed the design

Both demos that failed on their first run failed for real reasons, and the fixes are part of the build.

Finding 1 · Demo 5, run 1

LND with a remote Bitcoin Core backend cannot start a payment while that backend is unreachable. With A's bitcoind stopped, B's payment sat in flight with no HTLC attempt. B's log showed the router failing on a live getblockchaininfo call. Five minutes later LND's chain health check shut every node down, and a clean exit is not restarted by Restart=on-failure.

Fix: B and C run Neutrino with A as their only peer; A serves compact block filters over the mesh. The best-block view is then local, so payments need only the peer link. The systemd units use Restart=always. This was the plan's first follow-up item, pulled forward.

Finding 2 · Demo 4, run 1

After mining 1008 blocks at once, a wallet needs seconds to rescan before it can fund a channel. The reopen of A–B failed with "channels cannot be created before the wallet is fully synced". A regtest artifact, since mainnet never jumps 1008 blocks, but the scripts now wait for sync and retry.

Threat model

A is both the chain oracle for B and C and a channel counterparty on A–B and A–C. That conflict has to be stated plainly.

Case 1: A honest, C cheats while B is away

The 1008-block remote delay keeps C's funds locked long enough for B to come back. Demo 6 shows exactly this: B returned, saw the stale state through A, and took the channel one block later. A watchtower on A for the B–C channel would remove even the need to return in time; A is not a party to that channel, so A as tower is sound.

Case 2: A cheats

A could publish an old A–B state and hide it from B. With the original RPC backend B would have trusted A completely. With Neutrino, B verifies headers and proof of work itself: A can withhold blocks but cannot forge them. Withholding is still not detected automatically; that is the main open item.

Known gaps

  • A can still censor. B and C see only what A relays; a withheld block is invisible until someone notices stale timestamps. Not tested.
  • No watchtower. Case 1 relies on the timelock alone.
  • The gateway itself still uses the RPC backend and shares LND's can't-pay-without-chain limitation.
  • The ad-hoc WiFi link is unencrypted. Lightning traffic on it is end-to-end encrypted; the P2P block feed is authenticated by proof of work.
  • Regtest only. No public nodes, no real fees, wallets without seed backups.

What comes next, in order of value

  1. Watchtower on A for B–C. Closes case 1 without depending on the timelock. Built into LND.
  2. Detect a withholding gateway. Alert when the newest header is older than expected.
  3. Signet. A opens a channel to a public node; B pays someone on the internet through A, and opens a channel to a public node through A. "Offline node reaches the world."
  4. Isolation tests. Take B off the mesh during a pending close and measure recovery.
  5. Multi-hop reroute. Block the B–A radio path and show B still reaches A via C.
  6. Phone app layer. One web page on B: invoice QR, pay invoice, phone on B's hotspot pays C.
  7. Encrypt the mesh link (IBSS-RSN), then a second implementation (Core Lightning) on one node.

Reproduce it

The repository holds everything needed to rebuild from blank SD cards. Phase 0 (flashing, cabling, SSH keys) is done by hand; everything after that is scripted and was driven over SSH.
